## Finding 1 — Ghost screen-transition artifact on entry to NotifyMeScreen

**Severity**: MAJOR
**Lens**: 7 native-feel (primary), 2 motion (transition continuity)
**Rule doc**: n/a — experiential (native-feel lens question: "does anything feel web-like / janky?")
**Screen**: NotifyMeScreen (entry from UsageLimitSheet's "Upgrade to Macgie+")
**Build**: `625c895`

### What's off

Every path into `NotifyMeScreen` calls `usageLimitGate.dismiss()` then
`navigation.navigate('NotifyMe', ...)` synchronously in the same handler — this
exact pattern is repeated in all 4 call sites (`SettingsAboutScreen.tsx:102-108`
QA row, `SeeThisOnMeScreen.tsx:710-714`, `EnhanceImageScreen.tsx:392-396`,
`useAddWardrobeItem.ts:259-263`). Firing the push navigation before the sheet's
close animation has settled leaves a small, persistent, semi-transparent
floating snapshot of the screen (a miniature card with a drop shadow) stuck in
the top-left corner, behind the header, on every visit to `NotifyMeScreen` I
reproduced (3 separate captures over ~2 minutes, present every time). It reads
as a broken/glitchy transition — exactly what lens 7 asks to catch ("does
anything feel web-like?"). This lands on the one screen in the flow whose whole
job is to make "Macgie+ is coming soon" feel curated and worth waiting for
(lens 8); a stray ghost thumbnail undercuts that.

This is very likely a `react-native-screens` transition-snapshot/freeze
artifact triggered by navigating while the sheet is still mid-close — not
present on ordinary screen-to-screen navigation I captured elsewhere in this
session (Settings, About had no such artifact). qa-mobile's smoke report
(`plans/260814-1232-au-442-paywall-mvp/reports/qa-mobile-260814-1507-au-442-smoke-and-fix-verify.md`
§2) independently noticed "a small blurred/placeholder thumbnail... visible
top-left behind the header" on the same screen but did not file it — flagging
formally here since it reproduces consistently and sits squarely on an AU-442
surface.

### Evidence

- Source: `auxi/src/screens/settings/SettingsAboutScreen.tsx:102-108` (and the
  3 real trigger sites above) — the `dismiss(); navigate(...)` synchronous pattern
- Screenshot: `auxi/docs/design-reviews/screenshots/2026-08-14/designer-notify-me-screen.png`
  (top-left, behind header — zoom crop confirms it's a miniature snapshot of
  the destination screen, not a decorative asset)
- Also visible in: `auxi/docs/design-reviews/screenshots/2026-08-14/designer-notify-me-confirmed.png`
- Prior sighting (unfiled): qa-mobile smoke report §2, `qa-mobile-au442-notify-me-screen.png`

### Routing

- **mobile-dev** — investigate the sheet-dismiss + immediate-navigate timing
  (likely needs the navigate to wait a tick / next frame after `onDismiss`, or
  a `react-native-screens` freeze/snapshot config check) across all 4 call sites,
  not just the QA row.

## Finding 2 — "We'll notify you" confirmed state reads as disabled, not success

**Severity**: MAJOR
**Lens**: 5 component state coverage (primary), 8 recommendation/trust-experience
**Rule doc**: color-rules.md §2 (state accents — `green` reserved for
radio/confirm) — experiential judgment call on top of it
**Screen**: NotifyMeScreen, post-tap "Notify me" state
**Build**: `625c895`

### What's off

Tapping "Notify me" swaps the label to "We'll notify you" and applies
`MButton`'s standard `disabled` treatment (`opacity: 0.5` on the solid `ink`
fill → washed-out mid-gray, `MButton.tsx:186`). That's the *same* visual
language the design system already uses everywhere for "this control can't be
used right now" (a genuinely disabled row/button). There is no color shift
toward the system's confirm/success accent (`ds.color.green`, reserved per
color-rules.md §1-2 for radio/confirm), no checkmark, no other affirmative
signal. A user who taps "Notify me" and watches the button go flat gray is as
likely to read that as "my tap didn't register" as "you're confirmed" — on a
screen with no toast and no other acknowledgement, that ambiguity matters more,
not less. This is exactly the risk called out in the dispatch ("does this read
as broken/unresponsive?") — the answer is yes, plausibly.

The *mechanism* here (label swap + `disabled`, no toast, no new component) was
an explicit CEO-locked decision (extraction locked decision #4) and mobile-dev
implemented it faithfully — this finding is not second-guessing that mechanism.
It's flagging that the specific visual result of "disable the button" happens
to collide with the system's own "broken/unavailable" signal, at the one moment
this screen most needs to read as "success."

### Evidence

- Source: `auxi/src/screens/NotifyMeScreen.tsx:126-136` (disabled-on-`notified`)
  + `auxi/src/components/design-system/lib/MButton.tsx:186` (`disabled: { opacity: 0.5 }`)
- Screenshot: `auxi/docs/design-reviews/screenshots/2026-08-14/designer-notify-me-confirmed.png`

### Routing

- **mobile-dev** — apply a distinguishable confirmed treatment within the
  locked mechanism (e.g. swap the fill toward `ds.color.green` or keep `ink`
  fill with a leading check glyph, rather than the generic disabled-opacity
  token) — a token-level fix, not a new component.
- If the intended read genuinely is "just inert, that's fine for MVP" — that's
  a taste call; **CEO** should confirm before mobile-dev spends time on it.

## Finding 3 — NotifyMeScreen header says "Upgrade" on what is actually a waitlist

**Severity**: ESCALATE
**Lens**: 3 hierarchy / 8 trust / journey continuity
**Rule doc**: n/a — taste/product-direction call, Figma-approved copy
**Screen**: NotifyMeScreen
**Build**: `625c895`

### What's off

The user's flow is: tap **"Upgrade to Macgie+"** on the sheet → land on a
screen whose header title is **"Upgrade"** → read "...is coming soon." → the
only CTA is **"Notify me"**. The header literally uses the same title
(`notifyMe.title` = `"Upgrade"`, same string as `upgrade.title` on the real
`UpgradeScreen`) as the actual paywall, on a screen that cannot process a
purchase. Applying the "where was I / where am I / what should I do next"
journey-continuity check: a user who tapped an "Upgrade" CTA and now sees an
"Upgrade" header has every reason to expect a purchase flow; discovering
mid-read that it's a waitlist is a small trust cost right at a demand-gauging
moment where trust is the entire point.

This is **not** a code drift — the extraction confirms Figma's own frame
(`5078:13760`) literally specifies the header center label as "Upgrade," and
qa-ui verified the implementation matches. So this is a Figma-authored
decision, not something mobile-dev invented. Whether "Upgrade" is the right
header for a coming-soon/waitlist screen is a taste/positioning call, not a
system violation — routing to CEO rather than failing the gate on it alone.

### Evidence

- Source: `auxi/src/screens/NotifyMeScreen.tsx:96` (`title={t('notifyMe.title')}`),
  `auxi/src/translations/en-EN.json:996` (`"title": "Upgrade"`)
- Screenshot: `auxi/docs/design-reviews/screenshots/2026-08-14/designer-notify-me-screen.png`
- Figma: node `5078:13760`, confirmed in
  `plans/260814-1232-au-442-paywall-mvp/figma-extraction-paywall-sheet.md` §Frame 2

### Routing

- **CEO** — confirm intent: is "Upgrade" the right header for this MVP waitlist
  screen, or should it read something more honest to its function (e.g.
  "Coming soon")? If CEO confirms "Upgrade" is intentional (keeps messaging
  consistent with the future real paywall), no code change needed — record the
  decision and close.
